# Friday: expanded acceptance scenarios

_21 October 2026 · 76 original proposed scenarios (64 initial + 12 additional) · Online primary-source research plus generated examples · No device execution_

This is the next acceptance catalogue for Friday's coordinator, context and app handoffs. It extends the [existing 60 workflow specifications](30-online-usecase-catalog.md) and their [typed companion](online-usecases.json), concentrating on follow-up replies, source freshness, collection scope, ambiguity and recovery. The earlier T01–T60 identifiers and specifications stay authoritative for their basic workflows; UC01–UC76 below describe additional variations, rather than counting variations as distinct implemented capabilities.

**Every row is proposed and unrun.** These queries were authored for this document, not copied from benchmark prompts or drawn from private chats. Source links establish specific platform/product affordances or constraints. They do not establish that Friday can automate a named app, read every message, or complete a booking. Availability must be checked against the installed app version, account, permissions and exposed controls.

This catalogue is separate from the frozen [84-case SLM language regression](../tests/slm-regression.json). It is not training data, model-selection data, or an additional score for that regression. Language interpretation, real field entry, data collection and verified task completion need separate results.

## Sources and technical boundaries

**Benchmark method.** AndroidWorld supplies parameterized Android tasks and evaluates persistent task outcomes; AndroidControl contains human demonstrations with goals, step instructions, screenshots, accessibility trees and actions. Borrow the separation between a requested outcome, its UI trajectory and its grader. These sources support test design, not commercial-app compatibility. [AndroidWorld](https://github.com/google-research/android_world), [AndroidControl](https://github.com/google-research/google-research/blob/master/android_control/README.md)

**Access method.** Android isolates private app data. Plausible Friday data paths are an authorized provider/API, foreground accessible UI, or an app's share/export flow with a granted content URI. A generic assistant has no automatic access to another app's private database. [Android application sandbox](https://source.android.com/docs/security/app-sandbox), [AccessibilityService](https://developer.android.com/guide/topics/ui/accessibility/service)

Capability names in the tables describe proposed reusable operations, not a list of registered Friday executors. `UI` means observe the named app and validate its actual accessible controls. `Provider` means use an authorized Android provider. `URI` means selected/exported content with a valid grant. `Local` means Friday's stored task context, parsing, arithmetic or generation. An unavailable path must produce a specific unavailable/blocked result, with the retained task and missing prerequisite.

## Common run and evidence contract

Use synthetic contacts, messages, statements, files and test calendars. The examples assume a fixture clock of **21 October 2026, 09:00, Asia/Kolkata** unless the query supplies a different date or zone; actual device runs must record their real clock and locale. Fictional product and song names identify fixture data, not real recommendations or inventory.

For each attempt, record the selected Friday chat, task/step IDs, original query, supplied fields and their source, current app/account, app versions, interpreted plan, pending question, retry count and final outcome. Evidence belongs to the exact task revision and observed app state. A model's DONE, an app launch, a successful tap, a populated draft and a saved/sent record are distinct checkpoints.

Measure wall time from query submission through final verification, with separate interpretation/model-load, navigation, app/network wait, extraction, entry, readback and recovery durations. Keep user-wait time visible and separately attributed. No latency targets below are presented as measurements.

The query sets the action boundary: **draft** stays a draft; **read/search/compare** does not authorize a purchase or payment; an explicit **send/create/update** request must target the resolved recipient/record and be verified. Ask for genuinely missing or conflicting information, retain facts already supplied, and continue after the answer. Do not silently adopt old app fields as owner preferences.

## I. Spending patterns, holdings, activity, todos and note changes — UC65–UC76

These 12 additional scenarios are original proposals responding to the requested coverage of spending habits, investment holdings, Google Fit/activity, notes, todos and corrections. Use invented merchants, securities, quantities, activity records and notes. Financial and activity cases read and aggregate supplied facts; they give no investment, credit, medical or exercise advice, and authorize no trades, payments or health-record edits.

**Spending access.** CRED describes statement detection and spending insights, which supports proposing a bounded read flow. It does not establish a generic transaction-export API or Friday access to the owner's data. Use the actually accessible card view or a separately selected statement, with explicit coverage. [CRED card features](https://cred.club/cards)

**Investment access.** Zerodha documents a holdings report for a chosen date, downloaded as XLSX through Kite/Console. [Zerodha holdings report](https://support.zerodha.com/category/console/portfolio/console-holdings/articles/holding-report)

**Activity access, checked 21 October 2026.** Google's current migration guide says legacy Fit APIs are supported only until the end of 2026, recommending Health Connect for mobile step integrations. Do not assume new legacy Fit API access; inspect installed apps, available data and granted permissions. [Fit migration guide](https://developer.android.com/health-and-fitness/health-connect/migration/fit)

Health Connect supports time-bounded aggregates and source filters; Activity/Sleep deduplication follows the owner's app priorities. Raw sums across overlapping step sources are therefore an unsuitable default. Missing buckets need coverage checks. Older history and background reads have additional permission/availability constraints; a missing permission is not a zero observation. [Aggregation and source priority](https://developer.android.com/health-and-fitness/health-connect/aggregate-data), [Read access and history](https://developer.android.com/health-and-fitness/health-connect/read-data)

**Todo/note access.** Google documents Android task creation and editing, and Keep note creation/editing. An authorized API is a distinct adapter from UI automation: the Tasks REST `due` field stores a date and discards time, so it cannot prove a requested timed reminder. [Tasks on Android](https://support.google.com/tasks/answer/7675838?co=GENIE.Platform%3DAndroid&hl=en), [Tasks API fields](https://developers.google.com/tasks/reference/rest/v1/tasks), [Keep notes on Android](https://support.google.com/keep/answer/2888246?co=GENIE.Platform%3DAndroid&hl=en)
