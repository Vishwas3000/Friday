## Failures exposed in this round

### App and query interpretation

The fresh Maps-opening task card already bound `com.google.android.googlequicksearchbox` before navigation. The Maps-search card chose `web_search`, bound that same Google package and extracted `Maps for Cubbon Park Bengaluru` as its query; Chrome then opened. The first returned a truthful stuck response, while the search returned a completion claim. This directly localizes a failure before UI targeting. App-name matching is one implementation path to investigate; these observations do not prove it is the only cause.

### Exact text parsing

The synthetic request `Draft a message exactly: "QA-COVERAGE-73: 28 October 2026."` returned the surrounding quotation marks as message content. The declared expected content excluded those delimiters. The coordinator verified equality against its parsed input and marked completion, exposing an interpretation defect that downstream input equality did not catch. No model generated that output and no destination app received it.

### Writer quality and latency

The 20-case suite produced eight `ok`, seven expected `invalid`, one expected `length` and four `timeout` outcomes. One timeout was the deliberately tiny-deadline case; **W03 amount rewrite, W04 stay rewrite and W08 query cleanup unexpectedly timed out** near their 20-second deadlines. The sum of synchronous request intervals was **188.121 s**. Among eight accepted outputs only, app-reported total median was **14.035 s**, range **10.824–19.990 s**. These selected-output statistics are not an all-request success-latency score.

Mechanical passes include expected rejection/truncation/deadline outcomes. Qualitative review of accepted text found:

- W01 assigned an invented reminder role to a supplied reference.
- W05 copied the ungrammatical source unchanged.
- W06 omitted receipt acknowledgement and promised comments, while adding unsupported details wording.
- W10 strengthened a tentative meeting into an upcoming meeting.
- W12 included instruction content despite being asked to summarize only the parcel fact.
- W02 preserved the decline's facts but did not demonstrate polite rewriting; W07 produced a useful short title with comparison no longer explicit; W09 mostly preserved relationships with an undecided/uncertain wording concern.

No aggregate semantic accuracy is claimed from this manual review. Unlike the earlier memory-blocked run, this round generated text; no memory guard was lowered and unrelated apps were not forcibly stopped. App/memory/thermal conditions were not matched between rounds, so this does not establish an availability or speed improvement from a code change. The raw report's pending-review field is retained; judgments live in a separate review record.

### Evaluator and build findings

Three malformed records (`assistant:null`, `execution:null`, `timing:null`) escaped as `AttributeError` tracebacks. Positive infinity was accepted as a known wall duration. These five failing probes remain baseline findings; the evaluator has not been repaired to change their results.

## Three experiments tied to observed failures

### E1 — wrong app and wrong query

**Observed:** Maps requests reached Google/Chrome and returned false completion ([41](../research/41-capability-checkpoint.md)). Freeze those semantic cases plus new paraphrases. Compare the current versus stronger model stack under a pinned baseline versus persistent coordinator, using the same external package/query/result grader in all four arms. Keep available tools and screen modalities fixed or declare the difference. Add same-goal variants in alternative map apps; hold them out of tuning.

Measure unassisted goal completion, wrong-app rate, exact-input failures, false-success claims and end-to-end time. This distinguishes model selection/grounding failures from dispatch or verification defects. Design: [38 architecture](../research/38-navigation-architecture-and-harness-plan.md), [39 teachers](../research/39-teacher-model-options.md), [43 AnyAppBench](../research/43-anyappbench-paper-review.md).

### E2 — missing observations and unsupported capabilities

**Observed:** CRED exposed no readable application window; Gmail population lacked automatic readback ([41](../research/41-capability-checkpoint.md), [37](../research/37-pixel-research-live-acceptance.md)). Use synthetic readable, empty, wrong-app and permission-denied observations with the same requested output. Separately test one supported app live. Keep “source unavailable” distinct from an incorrect model action and from a broken grader.

Measure truthful blocked behavior, false totals/completions and observation coverage. A visual fallback is an isolated, permitted experiment with its own modality/runtime budget; it must not be assumed to read protected screens or repair the missing data. Design: [40 data/provenance](../research/40-navigation-data-and-training.md), [42 V-Droid](../research/42-vdroid-paper-review.md), [43 oracle/diagnosis boundaries](../research/43-anyappbench-paper-review.md).

### E3 — memory pressure and recovery

**Observed:** latest Writer generation was blocked by headroom, and research Resume required intervention ([37](../research/37-pixel-research-live-acceptance.md)). First profile the current tiny draft under ordinary cold/warm app states without killing unrelated apps or lowering memory guards. Then compare a compact model or explicit model-unload schedule under matched inputs. Test interruption/reconciliation in an isolated environment before real external writes.

Measure availability, accepted text quality, peak RAM, cold/load/prefill/decode/whole-task time, Stop latency, next-request success and duplicate real effects. A smaller model's file size or a stronger teacher's benchmark score is not a Pixel deployment result. Design: [38 execution contracts](../research/38-navigation-architecture-and-harness-plan.md), [39 teachers](../research/39-teacher-model-options.md), [40 single-GPU and Pixel gates](../research/40-navigation-data-and-training.md), [42 full-system evaluation](../research/42-vdroid-paper-review.md).

**Compact Pixel batch boundary:** use a dedicated verified test chat, preserve prior selection, and restrict live requests to app navigation, exact local text, one small local draft and read-only diagnostics. No sends, purchases, deletions, owner-data reset, blind legacy-suite execution or forced restart is part of that batch.
